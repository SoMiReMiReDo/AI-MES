用请求与测试定位失败

开工失败时，先分清是权限拒绝、业务规则阻挡，还是数据没有写入。像巡检一样沿途检查，每走一步都找一条证据。

从响应缩小范围

请求被拒绝

两个现有 API 开工用例中，跨产线操作员得到 403，同产线但前一道工序未完成得到 422。先找请求地址、身份和响应内容。Web 入口会通过页面反馈报告选线错误或业务异常。

成功返回，产量没变

先查该批是否完成、采用哪种流转模式，再查批次与工单的 produced_qty。整批模式下只完成首道工序时，工单产量还可以保持原值。

数据已变，页面没跟上

先重新读取数据。若重读正确，再检查网页是否刷新、实时订阅是否收到更新，以及当前页面使用的是哪种刷新方式。

一次提前开工的对话

这是根据源码和现有用例整理的演示。操作员已分配到该产线，但第一道工序仍未完成。

端
移动客户端

提交第二道工序的开工请求，携带操作员的访问令牌。

口
API 控制器

已核验该操作员可查看所属工单，把开工请求交给 BatchService。

规
BatchService

工序开工条件未满足。请先完成第一道工序，第二道工序保持原状态。

口
API 控制器

返回 422。客户端可以从 errors.step 中取出拒绝原因。

·
◎
同时看响应和存储结果

现有顺序用例核对拒绝原因，产量用例则重新读取工单后核对产量。前者能证明入口拒绝了请求，后者能证明数据库保存了预期结果。

从现有用例确认行为

在 BatchStepTest 中先对照三种结果。提前开工看第 65 行，末道工序计产看第 199 行，跨产线拒绝看第 289 行。

展开源码对照与验证命令

源码

逐行解读

第 74 行为测试用户签发访问令牌。这个场景模拟已登录的操作员。

第 76–77 行带着身份向第二道工序发出开工请求。

第 79–80 行要求响应为 422，且明确提示第一道工序未完成。

如果本地已有运行实例，可先请求 GET /api/health 看 HTTP 入口。生产行为用例需要 PHP 8.3、Composer 依赖和隔离的 SQLite 测试环境。准备好后，在仓库的 backend/ 目录执行：

php artisan test tests/Feature/Api/BatchStepTest.php --stop-on-failure
