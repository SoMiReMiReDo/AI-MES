1# 定制层级
2
3本文把 OpenMES 划分为四个层级，让职责与维护边界保持明确：**标准功能**、**配置**、**客户可维护的定制开发**、**厂商支持的定制开发**。
4
5当你需要判断一项改动应归属设置、模块、核心分支（fork）还是一份支持合作 —— 以及结果由谁负责 —— 就用本文做判断。

24<a id="why-this-split-matters"></a>
25## 为什么这个划分很重要
26
27OpenMES 是开源项目（AGPL-3.0），其设计目标是无需重写核心即可扩展。把「我们开了个设置」「我们装了个模块」「我们改了 Laravel 控制器」混作一谈，会让升级、支持和交接都变得痛苦。
28
29下面四个层级为任何一项能力回答三个实际问题：
30
311. **它是什么？**（定义）
322. **谁维护它？**（归属）
333. **你能得到什么样的支持？**（边界）
34

37<a id="quick-classifier"></a>
38## 快速分类器
39
40按顺序问这些问题：
41
42| 问题 | 若为是 → |
43|---|---|
44| 它随 OpenMES 核心一起发布，安装后无需写代码即可使用吗？ | **标准功能** |
45| 管理员仅通过 UI / `.env` / 数据配置就能实现，无需新增 PHP/JS 吗？ | **配置** |
46| 它需要代码，但只通过模块、钩子、API 客户端或其他不触碰核心的扩展点实现吗？ | **客户可维护的定制开发** |
47| 它改动核心（或需要深度 schema 改造），**并且**有商业支持 / 专业服务协议负责升级吗？ | **厂商支持的定制开发** |
48
49如果改动核心**却没有**支持协议，那它就是**不受支持的核心分支** —— 不是厂商支持的。优先选择模块（第 3 层）或签约服务（第 4 层）；见第 4 层下的提示框。
50
51如果两个答案都说得通，选择仍能满足需求且**侵入性最小**的那个层级。
52

55<a id="1-standard-functionality"></a>
56## 1. 标准功能
57
58### 定义
59
60随 OpenMES 产品一并发布的能力：生产计划、工单、操作员流程、问题/安灯（andon）、报表、RBAC、审计日志，以及用户指南和 README 中记录的其他内置功能。使用它们无需任何站点专属代码。
61
62### 示例
63
64- 创建工厂、产线、工位与工艺模板
65- 排产工单（计划器 / 甘特图视图）
66- 操作员队列、工序完成、批次生产
67- 问题上报与升级
68- 主管仪表盘与 CSV 报表导出
69- 内置 REST API 端点与 Sanctum token
70- 随项目发布的**捆绑**可选模块（仅启用/禁用）
71
72### 谁维护它
73
74- **上游 OpenMES 维护者**（社区版本）负责缺陷与产品演进
75- 站点管理员应用更新；他们不掌握核心功能的设计
76
77### 支持边界
78
79- 就所发布的版本而言，覆盖范围包括项目文档、issue 与社区渠道
80- 错误配置不是产品缺陷（见「配置」）
81- 对核心的本地补丁**不是**标准功能 —— 它们会把工作移入定制开发层级
82

85<a id="2-configuration"></a>
86## 2. 配置
87
88### 定义
89
90通过**设置、主数据、环境变量以及启用随产品发布的模块**实现的站点专属行为 —— 不引入新的应用代码。只要配置变更停留在数据 / 环境 / 模块启用层面，而没有被写进被改动的核心文件，它们就能在升级中保留。
91
92### 示例
93
94- System settings（系统设置）：production period、overproduction、sequential steps（[管理员指南](admin-guide.md)）
95- 用户、角色、权限、班次、产线、产品类型、工艺模板
96- CSV/Excel 导入列映射方案
97- 供 ERP 或自动化客户端使用的 API token
98- MQTT / 机器连通性连接设置（[MQTT 连通性](mqtt-connectivity.md)）
99- 通过 **Admin → Modules** 启用或禁用已安装模块
100- 部署用的 `.env` 值（URL、数据库、`APP_DEBUG`、邮件等）
101
102### 谁维护它
103
104- **客户 / 站点管理员**（日常）
105- 集成商可在上线期间设置初始值；持续归属仍留在站点
106
107### 支持边界
108
109- 有文档记录且流程化的设置属于自助管理范围
110- 错误的主数据或环境值是运维问题，不是「定制开发」
111- 通过编辑 `backend/app/` 下的文件或改写迁移来「配置」某些东西**不是**配置 —— 那是定制代码
112

115<a id="3-customer-maintainable-custom-development"></a>
116## 3. 客户可维护的定制开发
117
118### 定义
119
120由客户（或其集成商）构建并拥有的代码或集成，使用**受支持的扩展点**，因此核心 OpenMES 仍可从上游升级。首选载体是 `modules/` 下的自包含模块，外加钩子/事件、公开 API，或调用 OpenMES 的外部服务。
121
122### 示例
123
124- `modules/MyPlant/` 下的工厂专属模块（新页面、表、Artisan 命令）
125- 针对工单 / 批次钩子的事件监听器（[HOOKS.md](../HOOKS.md)）
126- 从模块服务提供者注册的侧边栏条目与路由
127- 使用 token 调用 REST API 的外部脚本或中间件
128- 向文档化的连通性 API 投递数据的自定义 MQTT 或 REST 网关
129- **仅在**模块系统有意允许之处进行的主题或 Blade 覆盖
130
131### 谁维护它
132
133- **客户工程团队**（或其指定的承包商）
134- 除非站点专属模块代码被贡献并合并进项目，否则上游不拥有它
135
136### 支持边界
137
138- 社区支持覆盖扩展点的工作方式（模块、钩子、API）—— 不负责调试专有工厂逻辑
139- 客户负责测试、备份，以及在 OpenMES 升级后重新测试模块
140- 如果某个模块开始需要核心补丁才能工作，请把它重构到钩子/模块上，或把工作移到厂商协议下（第 4 层）—— 不要留下一个不受支持的核心分支
141
142技术操作指南：[技术文档](development.md)（模块系统）与 [HOOKS.md](../HOOKS.md)。
143

146<a id="4-vendor-supported-custom-development"></a>
147## 4. 厂商支持的定制开发
148
149### 定义
150
151在**商业支持 / 专业服务**协议下交付并归属的定制工作，由厂商承担升级与质保责任。典型范围包括核心应用改动、侵入式 schema 改造，或无法仅存在于客户自有模块中的长期分支。
152
153**厂商支持是一个支持状态限定词**，而不是「我们改了核心」的同义词。没有合同的核心改动**不是**本层级（见下文「不受支持的核心分支」）。
154
155当需求跨越产品边界、需要保证的升级路径，或客户不想自建 MES 工程师团队时，使用本层级。
156
157### 示例
158
159- 在付费路线图合作下必须进入主产品线的功能
160- 与厂商自有适配器的深度集成，以及对齐发布的测试
161- 在合同约定合并前移（merge-forward）计划下，直接应用于核心的热修复
162- 对定制化部署提供 SLA 支持（由项目的商业联系渠道提供）
163
164### 谁维护它
165
166- **厂商 / 专业服务团队**，按合同
167
168### 支持边界
169
170- 范围、SLA 与升级政策由商业协议定义 —— 而非仅由 AGPL 社区 issue 跟踪器决定
171- 当能在不留下永久核心分支的情况下满足需求时，优先把可复用部分贡献到上游，或打包成模块
172
173商业 / 支持工作的联系方式列在项目文档中（例如 [Contributing](CONTRIBUTING.md) 里的 `support@openmmes.com`，用于安全及相关渠道；付费合作请使用项目公布的商务联系方式）。
174
175### 不受支持的核心分支（不是第 4 层）
176
177未经协议对 `backend/`（或核心的私有分支）的单方面改动仍属于定制开发，但**不是**厂商支持的：
178
179- **站点自己承担每一次升级冲突**
180- 社区渠道不会吸收该风险
181- 交接时，请明确标注为**不受支持的核心分支**，然后二选一：(a) 重写到模块/钩子（第 3 层），或 (b) 将其纳入商业协议（第 4 层）
182

185<a id="configuration-vs-custom-code"></a>
186## 配置 vs 定制代码
187
188| 方面 | 配置 | 定制开发（客户或厂商） |
189|---|---|---|
190| 机制 | UI 设置、主数据、`.env`、启用模块 | 新 PHP/JS、模块、监听器、API 客户端、核心补丁 |
191| 需要开发者吗？ | 通常不需要 | 需要 |
192| 升级影响 | 只要不编辑核心文件就低 | 模块：重新测试；核心补丁：合并成本高 |
193| 典型归属 | 站点管理员 | 客户工程团队**或**合同下的厂商 |
194| 示例 | 打开 `force_sequential_steps` | 在 `WorkOrderCompleted` 时向 ERP 投递的模块 |
195
196**经验法则：**如果你能在 Admin / Settings / data import 里完成，而不用打开代码编辑器，那它就是配置。如果新增或修改了可执行代码，那它就是定制开发 —— 然后按上文各节选择「客户可维护（扩展点）」还是「厂商支持（核心 / 合同）」。

200<a id="ownership-and-support-boundaries"></a>
201## 归属与支持边界
202
203| 层级 | 主要维护者 | 升级责任 | 典型支持渠道 |
204|---|---|---|---|
205| 标准功能 | 上游项目 | 站点应用发布；上游修复核心缺陷 | 文档、GitHub issue、社区 |
206| 配置 | 客户管理员 | 客户（更新前备份数据/环境） | 文档 + 管理员运行手册 |
207| 客户可维护的定制开发 | 客户（或其集成商） | 客户重新验证模块/集成 | API/钩子看社区；逻辑归客户 |
208| 厂商支持的定制开发 | 合同下的厂商 | 厂商按合同 | 商业支持 / SOW |
209
210### 交接清单
211
212在团队之间移交一套部署时，列出每一项非标准项，并给它打上四个层级之一的标签：
213
2141. 使用的核心版本（标准）
2152. 与默认值不同的环境与系统设置（配置）
2163. 已安装的模块与外部 API 客户端（客户可维护的定制，除非归厂商所有）
2174. 付费 / SLA 支持的定制交付物（**厂商支持**）
2185. 任何单方面的核心差异或私有分支（**不受支持的核心分支** —— 不是第 4 层；规划重写或签约）
219
220评审者应当能挑出站点上的任一功能，并用本文把它归入恰好一个主要层级（或标记为不受支持的核心分支）。

224<a id="classifying-a-feature-worked-examples"></a>
225## 给功能分类（示例推演）
226
227| 功能 / 改动 | 层级 | 原因 |
228|---|---|---|
229| 操作员在平板上完成一道工序 | 标准 | 内置的产品行为 |
230| 要求所有工单都填写周数 | 配置 | 系统设置（`production period`） |
231| 从 Admin 启用 Packaging 模块 | 配置 | 启用随产品发布/已安装的模块；无新代码 |
232| 在物料短缺问题上给采购发邮件的模块 | 客户可维护的定制 | 模块 + 钩子；核心未动 |
233| 通过 REST API 创建工单的脚本 | 客户可维护的定制 | 基于公开 API 的外部客户端 |
234| 为一次性 UI 在核心中打补丁 `WorkOrderController`（无合同） | 不受支持的核心分支 | 无厂商归属的核心改动；重写为模块或寻求支持 |
235| 带 SLA 的整厂 WMS 桥接付费交付 | 厂商支持 | 商业归属与升级路径 |
