1# 推广上线：仓库与 ERP 同步（#212）
2
3仓储模块与 ERP 主数据 / 库存同步的部署运行手册。写来供不是在写这个功能的人，在生产环境上从上到下逐步执行。
4
5**对既有部署的改动：** 四张新表、`product_types` 上的三个新列、`material_lots` 和 `stock_movements` 上各一个新列、三个新的 API scope，以及一个新的可选模块。**在管理员启用该模块之前，任何东西都不会显示或被激活**——仅部署代码不改变任何行为。
6
7| | |
8|---|---|
9| **停机时间** | 仅容器重启（几秒）。迁移是增量的；没有表被重写。 |
10| **可回滚** | 是——见 [回滚](#rollback)。 |
11| **做一半就停的风险** | 低。未配置的代码是惰性的。 |

30<a id="1-before-you-start"></a>
31## 1. 开始之前
32
33**备份数据库和 `.env`。** 迁移是增量的，但回滚路径会删掉新表，而且期初库存的加载第一次做很容易出错。
34
35```bash
36docker compose exec -T postgres pg_dump -U openmmes_user openmmes \
37 > backup_pre_warehouse_$(date +%Y%m%d_%H%M).sql
38cp .env .env.backup_pre_warehouse
39```
40
41**提前决定仓库布局**——这是事后最难改的一件事，因为单据会引用仓库：
42
43- 要几个仓库？能用的最小数量是**两个**：一个原材料库和一个成品库。
44- 每一种里哪个是**默认**仓库？自动生成的单据，以及没有指定仓库的导入，都会落在那里。
45- 每个仓库在 ERP 里有没有**对应的编码**？现在就记下来；它填进 `ERP code` 字段，是两边对得上单据的关键。
46
47**确认谁负责库存。** 如果数量以 ERP 为准（通常是这种情况），OpenMES 的结存只是一个镜像：ERP 同步会**替换**它们。如果由 OpenMES 负责，那就根本不要跑库存导入。
48
49**检查当前版本**，这样回滚时能指名道姓：Admin → System → Updates，或 `git -C /opt/openmes describe --tags`。

53<a id="2-deploy-the-code"></a>
54## 2. 部署代码
55
56选择与部署管理方式相匹配的路径。
57
58### Docker Compose（自托管，最常见的情况）
59
60```bash
61cd /path/to/OpenMes
62git fetch --all
63git checkout main # or the release tag you are deploying
64git pull --ff-only
65
66docker compose up -d --build
67```
68
69entrypoint 会在启动时于**主**容器（Octane）上运行 `php artisan migrate --force`——边车会跳过它，因此没有竞态。观察它是否落地：
70
71```bash
72docker compose logs -f backend | grep -E "Running migrations|DONE|error"
73```
74
75### Admin → System → Updates
76
77也可以：更新流程会下载发布包、备份、复制、迁移并清理缓存。但无论如何，先做第 1 步的数据库备份——内置备份覆盖的是文件，不是数据库。
78
79### 无论走哪条路径
80
81```bash
82docker compose exec backend php artisan optimize:clear
83docker compose exec backend php artisan octane:reload
84```
85
86> Octane 会把框架常驻在内存里。不重新加载的话，新路由和配置可能看起来"不见了"——这是部署后最常见的"端点 404"报告。

118<a id="4-configure-warehousing"></a>
119## 4. 配置仓储
120
1211. **启用模块。** Settings → System → **Modules** → 勾选 **Warehouses** → Save。（从未自定义过模块组合的部署会自动开启它；已经保存过自定义组合的部署则会**关闭**它——这一步就是为此存在。）
1222. 如果角色受限，**授予标签页访问权限**：Admin → Access → `warehouse` 标签页，给应该看到它的角色。
1233. **创建仓库**——Admin → Production → Warehouses → All Warehouses：
124 - 编码、名称、**类型**（`Raw materials` / `Finished goods` / `Mixed`），
125 - 适用时填 **ERP code**，
126 - 每种类型中，在一个仓库上勾选 **Default for its kind**。
1274. **决定是否自动生成单据。** 默认情况下，完成一张工单会创建一份草稿的物料出库单和一份草稿的产品入库单。要关掉它：
128
129 ```bash
130 # .env
131 WAREHOUSE_AUTO_DOCUMENTS=false
132 ```
133
134 然后执行 `docker compose up -d backend && docker compose exec backend php artisan config:cache`。
135
136 除非 ERP 会自己创建这些单据，否则保持开启。生成的单据是**草稿**——过账之前不会移动任何库存。
1375. **为每条产线指定其库存地点。** Admin → Lines → *Stock location*。产线上记录的消耗会从物料实际来源的地点扣减：如果拣选时知道**被拣批次**，就扣它的仓库；否则扣产线的库存地点；再否则扣默认原材料仓库。每次扣减都会写一条带该仓库的 `stock_movements` 行。没设库存地点的产线照样能跑——它会回退到默认值——而在 Warehouses 模块关闭时，消耗完全不移动任何地点结存。
1386. **检查负库存策略。** Settings → System → *block negative stock*。开启后，过账一份会让某物料跌破零的出库单会被拒绝——**某地点覆盖不了的车间消耗**也一样会被拒绝（第 5 步）——这在期初库存加载完之后正是你要的，之前则很折磨人。先加载期初库存，或者在切换完成之前先关掉这个设置。
139
140到这里 UI 已经能用了，但还没有任何东西被同步。

144<a id="5-load-opening-stock"></a>
145## 5. 加载期初库存
146
147顺序很重要：必须先生成条目，批次或结存才能引用它。
148
1491. **物料和产品**——通过现有的 CSV 导入、管理员 UI，或 ERP 主数据端点（第 6 步）。
1502. **追踪批次的物料 → 带数量的批次**（`/erp/material-lots/import`，或 Admin → Materials → Material Lots 手工录入）。针对某个仓库导入批次，同时会写入该仓库的结存，并重新推导物料的全局数量。
1513. **其余一切 → 结存快照**（`/erp/stock/import`）。对于不追踪批次的物料和成品，这是正确的工具。
1524. **对账。** 物料显示的全局 `stock_quantity` 必须等于其各仓库合计之和：
153
154 ```bash
155 docker compose exec -T postgres psql -U openmmes_user -d openmmes -c "
156 SELECT m.code,
157 m.stock_quantity AS global,
158 COALESCE(SUM(ws.quantity), 0) AS warehouses
159 FROM materials m
160 LEFT JOIN warehouse_stocks ws
161 ON ws.material_id = m.id AND ws.material_lot_id IS NULL
162 WHERE m.deleted_at IS NULL
163 GROUP BY m.id, m.code, m.stock_quantity
164 HAVING ABS(m.stock_quantity - COALESCE(SUM(ws.quantity), 0)) > 0.001;"
165 ```
166
167 **零行才是通过条件。** 只要有任何一行，就说明有某个结存是由跳过了对账的路径写入的——停下来调查，别上线，因为分配引擎和 MRP 读的是这个全局数字。
168
169> 批列（lot 列）为空的结存行，是该物料在那个仓库的**总量**；带批次的行走它的明细。永远不要把这两者相加。

173<a id="6-connect-the-erp-optional"></a>
174## 6. 接入 ERP（可选）
175
176只有当需要 ERP 给 OpenMES 供数时才需要。除 **Warehouses** 外，还需要 **ERP integration** 模块。
177
178### 6.1 签发密钥
179
180Admin → API keys → new key。只授予集成真正需要的权限：
181
182| Scope | 用于 |
183|---|---|
184| `erp:masterdata:write` | 产品、物料、批次、配方 |
185| `erp:stock:write` | 结存快照、确认单据 |
186| `erp:stock:read` | 读取结存、轮询单据积压 |
187| `erp:orders:import` | 工单 |
188| `erp:production:read` | 生产完工 |
189| `erp:quality:read` | 质量 / 不合格导出 |
190
191密钥只显示**一次**。把它存进 ERP 一侧的密钥库；如果 ERP 地址固定，就配置 IP 白名单和有效期。
192
193### 6.2 同步顺序
194
195第一次同步按这个顺序执行——每一步都会解析下一步要用的编码：
196
1971. `POST /api/v1/erp/products/import`——把 `only_categories` 设为真正是制造产品的那些分类。
1982. `POST /api/v1/erp/materials/import`——设为原材料 / 包装分类。
1993. `POST /api/v1/erp/boms/import`——配方；需要产品**以及**每个产品的工艺模板。
2004. `POST /api/v1/erp/material-lots/import` 和/或 `POST /api/v1/erp/stock/import`。
2015. `POST /api/v1/erp/work-orders/import`。
202
203**每步先用两三行做试运行。** 每个导入都会返回逐行报告；`207` 表示有部分行失败，并告诉你是哪些：
204
205```json
206{"data":{"imported":2,"updated":0,"skipped":1,
207 "errors":[{"row":3,"field":"material_code","message":"Material 'GHOST' not found"}]}}
208```
209
210等小批量返回干净结果后，再扩展到完整负载。大小限制：每次请求 2000 个产品/物料、5000 个批次或结存、500 个配方、1000 张工单。
211
212### 6.3 拉取一侧
213
214ERP 通过登记 OpenMES 的单据来闭环：
215
216```bash
217# What has OpenMES posted that the ERP has not booked yet?
218curl -s "https://mes.example.com/api/v1/erp/stock-documents?unsynced_only=1" \
219 -H "X-Api-Key: $KEY"
220
221# ...book it in the ERP, then hand the ERP's own number back
222curl -s -X POST "https://mes.example.com/api/v1/erp/stock-documents/$ID/ack" \
223 -H "X-Api-Key: $KEY" -H 'Content-Type: application/json' \
224 -d '{"erp_reference":"RW-2026/00042"}'
225```
226
227主数据和结存**每晚**同步一次，单据积压每 **5–15 分钟**同步一次。在读取端点用 `?since=<last successful sync>` 做增量轮询，并沿着 `meta.next_cursor` 一直跟到它为 null。
228
229完整参考：[API documentation → ERP Integration API](API_DOCUMENTATION.md#erp-integration-api)。

233<a id="7-acceptance-test"></a>
234## 7. 验收测试
235
236交付之前，在正式环境上跑一遍。它会检验每个活动部件，除了一张工单的单据之外不留任何残留。
237
238| # | 步骤 | 通过条件 |
239|---|---|---|
240| 1 | 打开 Admin → Production → Warehouses | 列出了仓库，每种类型有一个默认 |
241| 2 | 打开 Stock On Hand | 期初结存与 ERP / 实盘数一致 |
242| 3 | 完成一张小批量工单 | Stock Documents 上出现两份**草稿**单据，都关联到该工单 |
243| 4 | 打开物料出库单 | 明细行与工单消耗一致（已记录的批次，或 BOM × 产量） |
244| 5 | 过账 | 状态为 `posted`；仓库结存正好减少各明细行数量 |
245| 6 | 重新运行第 5 步的对账查询 | 零行 |
246| 7 | 取消同一份单据 | 结存回到过账前的值；流水中有两条移动记录，净额为零 |
247| 8 | `GET /erp/stock-documents?unsynced_only=1` | 已过账的单据连同其明细行出现 |
248| 9 | `POST /erp/stock-documents/{id}/ack` | 单据离开积压列表，带上 ERP 参考号 |
249| 10 | 原样重跑一次主数据导入 | 结果是 `updated` 而非 `imported`；数量不变（同步是收敛的） |
250
251任何一步失败 → 停下，不要继续加载剩余的期初库存，并检查 `storage/logs/laravel.log`（导入失败会记录完整原因；API 响应则有意不记录）。

255<a id="8-first-week-of-monitoring"></a>
256## 8. 第一周的监控
257
258```bash
259# Import and generation failures
260docker compose exec backend tail -n 200 storage/logs/laravel.log \
261 | grep -E "ERP import row failed|Could not generate stock documents"
262```
263
264盯三件事：
265
266- **单据积压没有增长。** `unsynced_only=1` 的数量上升，说明 ERP 停止确认了——是它那一侧的闭环断了，不是我们。
267- **没有漂移。** 第一周每天运行第 5 步的对账查询。
268- **草稿正在被过账。** 堆了一堆旧草稿，说明过账这一步没人负责；决定是由人来做还是由 ERP 来做。

272<a id="rollback"></a>
273<a id="9-rollback"></a>
274## 9. 回滚
275
276按推广的相反顺序回滚。选能解决问题的最浅层级。
277
278**第 1 级——关掉功能（几秒，无数据丢失）。** Settings → System → Modules → 取消勾选 **Warehouses**。页面消失，`/erp/stock*` 端点返回 404，自动生成停止。数据保留。这几乎是任何问题的正确第一步。
279
280**第 2 级——只停掉自动单据。** `WAREHOUSE_AUTO_DOCUMENTS=false` + `config:cache`。保留 UI 和 API。
281
282**第 3 级——回退代码，保留 schema。**
283
284```bash
285git checkout <previous tag>
286docker compose up -d --build
287docker compose exec backend php artisan optimize:clear
288```
289
290新表会留在那里，不被使用，也无害。**优先于第 4 级。**
291
292**第 4 级——删除 schema（会销毁仓库数据）。**
293
294```bash
295docker compose exec backend php artisan migrate:rollback --step=6 --force
296```
297
298这会删除所有仓库、结存和单据，并移除新列。由过账写入的 `stock_movements` 行会保留（只是它们的 `warehouse_id` 列没了），因此物料流水仍然可读。先做一次新的备份——没有备份这一步不可逆。

302<a id="10-known-gotchas"></a>
303## 10. 已知坑
304
305| 现象 | 原因 | 解决办法 |
306|---|---|---|
307| 部署后新端点 404 | Octane 仍在提供旧的启动实例，或模块未开启 | `octane:reload`；检查 Settings → Modules |
308| 某个角色看不到仓库页面 | 该角色没有 `warehouse` 标签页的访问权限 | Admin → Access |
309| 完成工单时没有生成单据 | 模块已关闭、`WAREHOUSE_AUTO_DOCUMENTS=false`，或该类型没有默认仓库 | 第 4 步 |
310| 导入返回 `207` 和 `Row could not be processed` | 数据库层面出了问题；这条消息是刻意做得笼统的 | `storage/logs/laravel.log` 里有真正的原因 |
311| 结存看起来少了一半或多了一倍 | 把某物料的合计加到了它自己的分批行上 | 把无批次的行报为合计；有批次的行是明细 |
312| 全局库存与各仓库不符 | 有结存是由跳过了对账的路径写入的 | 用第 5 步的对账查询，然后重跑库存导入 |
313| 过账被拒："would drive below zero" | `block negative stock` 开着，而期初库存不足 | 加载期初库存，或在切换期间清除该设置 |
314| 消耗被拒："location does not hold enough" | `block negative stock` 开着，而该地点的结存不足 | 加载它的期初库存、把库存调过去，或在切换期间清除该设置 |
315| 消耗从错误的库房扣减 | 该地点在第一次扣减时就被冻结在分配上 | 检查被拣批次的仓库和产线的库存地点；后续更正是因为把物料让出来的那个库房回补 |
316| ERP 同步让库存不断膨胀 | 把导入当成了增量 | 它是快照——发送当前数量，而不是变化量 |
