1# Production flow deployment and rollback
2
3The quantity-ledger migration is
4`2026_09_15_100000_add_flow_ledger_to_batch_steps.php`.
5It changes step counters to decimals, adds step scrap and permits unclassified scrap reasons.
6Whole-batch mode remains the default until transfer mode is enabled in production settings.

8## Upgrade
9
101. Stop production writes, including operator requests, connectivity pollers and queue workers.
11 HTTP maintenance mode alone does not stop machine or background writes.
122. Take and verify a database backup. Rehearse the migration with a production-sized copy to
13 measure ALTER TABLE/backfill locking time; the test database does not establish downtime.
143. Deploy the backend and built frontend, then run `php artisan migrate --force`.
154. Restart long-running application/queue/connectivity workers with the new code.
165. Verify whole-batch operation, then enable transfer mode during a controlled production pause.
17 Confirm existing batch quantities and machine counter semantics before resuming production.

19## Schema rollback policy
20
21A downgrade is permitted only while the old schema can represent the stored values. Before
22any schema modification, the migration refuses rollback if any of these exist, including
23soft-deleted rows:
24
25- a scrap entry with no reason;
26- a nonzero step scrap counter;
27- fractional, negative or greater-than-2147483647 passed quantities.
28
29Refusal leaves the schema and production facts intact and tells the operator how to proceed.
30The policy deliberately avoids assigning a fabricated scrap reason, dropping scrap history
31or rounding production quantities just to make rollback succeed. Compatible data can roll
32back and migrate forward again; this is covered on SQLite and PostgreSQL.
33
34Once incompatible production data exists, use a forward correction. If a return to the old
35schema is unavoidable, stop all writers, preserve a backup/export of the current state,
36restore the verified pre-upgrade database together with its matching application version,
37and reconcile production recorded since that backup before resuming. Restoration alone does
38not preserve post-backup production. Do not bypass the rollback guard or assume deploying an
39older application against this schema has been validated.
40
41## Backward-compatible upgrades and optional channel migration
42
43The additional migration is `2026_09_15_120000_create_machine_counters.php`. It introduces
44durable channel state and retained reading/reconciliation history. **Existing machine integrations
45keep their legacy behaviour after an upgrade.** Opening a source in Machine counters does not
46opt it in. No new timestamps, event IDs or assignments are required for legacy whole-batch
47counting. Previously configured explicit channels remain explicit.
48
49Enable **explicit counting** for one channel at a time when ready. MQTT, Modbus and OPC UA all
50support the explicit pipeline. Its assignment, timestamp and event-ID requirements below apply
51only after that channel opts in. Legacy counting keeps its previous reset/routing assumptions;
52those reliability improvements are part of the explicit mode.
53
54Production flow is currently **system-wide**, not per order or per channel. Migrate channels
55while whole-batch flow remains enabled. The web and API settings endpoints refuse transfer
56flow when open machine-counted work has incompatible legacy channels or its existing output
57does not match the step ledger. Finish/reconcile that work first. Runtime guards also prevent
58legacy sources from writing a transfer ledger if settings are changed outside those endpoints.
59Manual-only orders do not require machine-channel migration.
60
61Pause acquisition around a channel switch. To opt in, choose its configuration, enter a reason
62and click **Enable explicit counting**. To opt out, use **Return to legacy counting** with a
63reason while in whole-batch flow. Both transitions retain audit history. Returning a tag to
64legacy mode clears its old cache baseline; its next reading establishes the legacy baseline
65without replaying the interval spent in explicit mode.
66
671. In **Connectivity → Machine counters**, open each good/reject/cycle tag or production MQTT
68 mapping. Select its mode and quality meaning explicitly.
692. Set its workstation and the exact batch step. Multiple batches can run at a workstation;
70 a channel targets only its explicitly assigned step. Only one good-count channel may be
71 assigned to a step. Unassign that channel before replacing it with another source.
723. In explicit mode, use an **exact MQTT topic**, without `+` or `#`. Legacy wildcard topics
73 continue working until migrated. Existing `line_id`, `step_number`,
74 `order_no`, `order_id` and `also_count_work_order` counting hints no longer choose the target.
75 The final effective step owns finished output; intermediate counts never add order output.
764. Supply acquisition timestamps on **all** count readings. Gateways use `ts`; MQTT defaults
77 to `$.timestamp` (or `action_params.timestamp_path`). Use ISO 8601 with a timezone, preferably
78 UTC. Preserve the acquisition time across retries; synchronise device clocks. The Modbus
79 poller stamps the time it acquires a register reading.
805. For increment/pulse channels, also supply a stable event ID: gateway `event_id`, MQTT
81 `$.event_id` (or `action_params.event_id_path`). IDs must remain identical on retries and
82 must not be reused for new events, including after device restart or batch changes.
83 **A polled boolean is not a deduplicated pulse:** use a cumulative register or a publisher
84 that provides a distinct event ID and acquisition time for each pulse. A pulse has value 1.
856. Send the first cumulative reading as a baseline. Verify the next known increment against the
86 physical machine and the intended step. The baseline is independent of existing order
87 output; 50,000 then 50,003 means 3 new pieces, even if order output was already nonzero.
887. Resume the migrated channel only after checking assignment, quality meaning and timestamp/event-ID
89 delivery. Batch changes require explicit reassignment. Stop or establish a known boundary
90 at the machine when changing batches: output between reassignment and the next cumulative
91 baseline is intentionally not inferred. Reconcile that transition using physical evidence.
92
93Counts use the ledger's two-decimal quantity precision. Negative, nonnumeric, over-range and
94higher-precision values are retained as invalid; they do not advance the baseline. Accepted
95raw values are limited to 999,999,999,999.99. Excess production beyond the step's available
96quantity remains recorded as a partial reading for review.
97
98Only **good** counts advance the step. Total counts with unknown quality and reject counts are
99retained for quality review; they do not automatically create good output or step scrap.
100Scrap reporting/classification continues through the existing production workflow. Legacy
101MQTT direct step-completion/order-status mappings are rejected for transfer-ledger orders;
102complete them through that workflow so quantity, blocking and completion rules run.
103
104## Machine concurrency and recovery
105
106In explicit mode, a channel row lock serializes its baseline, assignment and event-ID lookup.
107That same lock serializes both modes with configuration changes, so an in-flight legacy
108reading cannot race an opt-in and also be processed by the explicit path. Production then
109locks the order and step in the same order used by the ledger. The baseline change, accepted
110production and reading history commit together. Cache flushes and worker restarts do not
111lose baselines or duplicate-detection history.
112
113A decreasing cumulative reading freezes the channel until reviewed. Later larger values do
114not silently resume counting. Reset acknowledgement clears the baseline; the next fresh
115reading establishes it without adding output. Source/address/transform/mapping changes require
116saving and validating configuration again, rather than bypassing that check with a reset.
117Pause acquisition when changing source settings, restart/reload the gateway or poller, and then
118verify a fresh baseline before resuming. The built-in Modbus path also rejects readings decoded
119with a stale tag or transport snapshot; external gateways must honour their refreshed config.
120
121Unassigned, blocked and partial readings stay in **Awaiting review**. Supervisors can apply an
122entire remaining good delta to a compatible open step, or dismiss it with a reason. Original
123readings retain their original attribution; reconciliation is appended separately. A failed
124reconciliation rolls back any partial production write. No automatic replay occurs on resume.
125
126The counter migration refuses rollback once reading/audit history exists, including initial
127configuration. Use a forward migration or the verified backup-recovery process above. Deleting
128history or baselines to make a rollback succeed can reintroduce duplicate production. Source
129soft deletion remains available; hard purges are constrained while counter evidence references
130those sources.

134## Flow changes and manual corrections
135
136Changing from transfer to whole-batch flow is refused while any nonterminal routed order
137remains open, including orders with no output yet. Finish or cancel these orders first.
138Omitting the flow field preserves its current value. Settings imports intentionally ignore
139`production_flow_mode`; change it separately through System settings or the validated API.
140
141The built-in Modbus poller accepts **cumulative** explicit counters only. For pulse/increment
142production, use a gateway that preserves acquisition timestamps and stable event IDs.
143Repeated polling of a boolean does not identify physical pulses.
144
145With **Production Quantity Corrections → Full edit** enabled, the operator who started the
146step (or a Supervisor/Admin) can correct a running Operator-counted step in transfer mode.
147Timed windows apply to individual shift entries, not aggregated step totals. **Correct good quantity** accepts the
148corrected total and a mandatory reason. It records before/after totals and the user in the
149immutable audit log. Stale forms, stopped production, completed steps, machine-counted orders,
150quantities above incoming pieces, and reductions below downstream consumption are rejected.
151Correct downstream steps first when necessary. This action does not edit scrap or reopen
152completed work; investigate those discrepancies before closing affected work.
153
154Counter migration rollback is refused as soon as a counter exists, even without readings.
155Configuration and assignments are production state too; use the recovery policy above.
