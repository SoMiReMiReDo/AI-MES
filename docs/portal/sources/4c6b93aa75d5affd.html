29## 许可
30
31OpenMES 是开源软件：
32
33- **核心**以 **GNU Affero General Public License v3.0 (AGPL-3.0)** 发布；
34- **模块层**（`modules/`）以 **Academic Free License 3.0 (AFL-3.0)** 发布，因此模块可以是闭源/专有的。
35
36OpenMES **也**可能以单独的**商业**许可条款提供。这种双许可模式为持续开发提供资金，同时让开源社区始终能获得 AGPL 许可的版本。

40<a id="contributor-license-agreement"></a>
41## 贡献者许可协议
42
43> **你保留自己的版权。OpenMES 保持开源。CLA 允许我们以附加许可（包括商业许可）提供 OpenMES。**
44
45在我们合并你的**第一份**贡献之前，请签署 OpenMES 贡献者许可协议（[CLA.md](../CLA.md)）。
46
47**CLA 意味着什么**
48- 你**保留**对自己作品的**版权**——CLA **不会**转移你贡献的所有权。
49- 你授予项目所有者必要的权利，使其能在 OpenMES 中使用你的贡献，并以开源和商业两种模式许可 OpenMES。
50- 你仍可自由地在其他地方使用和许可你自己的贡献。
51- 你确认你有权贡献你所提交的代码。
52
53**为什么要求它**——没有贡献者协议时，每位贡献者都对自己的贡献持有版权，随着项目发展，一致的双许可模式将无法实现。CLA 让 OpenMES 能继续以开源形式发布，提供为开发提供资金的商业/SaaS 选项，并在无需让所有人重新签署的情况下把管理权移交给未来的公司。
54
55**如何签署**——打开你的 pull request；如果需要签名，机器人会发表评论。用它所要求的原文短语回复：
56
57```
58I have read the CLA Document and I hereby sign the CLA
59```
60
61你的签名覆盖你过去和未来的所有贡献。它只记录一次；之后的 PR 不会再询问（直到 CLA 版本变更）。
62
63**为雇主所做的贡献**——如果你的雇主或其他组织拥有你作品的版权，除非你有授权，否则**不要**代表它接受个人 CLA。请先联系维护者——可能需要一份企业 CLA（[`docs/cla/CCLA-template.md`](cla/CCLA-template.md)）或其他授权，在它到位之前 PR 不会被合并。
64
65**第三方代码**——除非其许可与 OpenMES 兼容，否则不要提交从其他项目复制的代码；在你的 PR 中标明其来源与许可。
66
67**AI 生成的代码**——如果实质性地使用了 AI 工具，请在 PR 中适当披露。是你运行了工具，也要对结果负责；据你所知，它不得包含采用不兼容许可的第三方代码。提交必须带有**人类作者**（AI 至多作为 `Co-authored-by` 署名）。
68
69**琐碎改动**——**≤ 20 行且不含新逻辑**的改动（拼写错误、格式化、显而易见的修复）不需要 CLA；维护者可以给该 PR 打上 `cla: trivial` 标签并合并。
70
71接受 CLA 会记录你的 GitHub 用户名、日期和文档版本。隐私说明见 [CLA.md](../CLA.md#personal-data-gdpr)。

77

105## 提交更改
106
1071. 在 GitHub 上 **Fork** 仓库
1082. 从 `main` **创建分支**：
109 ```bash
110 git checkout -b feature/my-feature
111 # or
112 git checkout -b fix/issue-description
113 ```
1143. 遵循下面的指南**进行你的修改**
1154. **运行测试**——所有测试必须通过：
116 ```bash
117 php artisan test
118 ```
1195. **运行格式化工具**：
120 ```bash
121 ./vendor/bin/pint
122 ```
1236. **提交**你的更改（见 [提交信息约定](#commit-message-convention)）
1247. **推送**并针对 `main` 开一个 Pull Request

128<a id="pull-request-guidelines"></a>
129## Pull Request 指南
130
131- **每个 PR 只做一个功能**——保持 PR 聚焦、易于评审
132- **包含测试**——新功能和 bug 修复必须包含测试覆盖
133- **更新文档**——如果改动影响用户可见行为，更新相关文档文件
134- **描述改动**——在 PR 描述中解释你改了什么、为什么改
135- **引用 issue**——用 `Closes #123` 或 `Fixes #456` 链接相关 issue
136
137### PR 检查清单
138
139- [ ] 已编写测试并通过（`php artisan test`）
140- [ ] 代码已格式化（`./vendor/bin/pint`）
141- [ ] 没有带用户输入的裸 SQL
142- [ ] 后端校验走 Form Request
143- [ ] 鉴权检查已到位
144- [ ] 没有无理由地新增依赖

148<a id="commit-message-convention"></a>
149## 提交信息约定
150
151我们遵循 [Conventional Commits](https://www.conventionalcommits.org/)：
152
153```
154<type>: <short description>
155```
156
157类型：
158| 类型 | 用途 |
159|---|---|
160| `feat` | 新功能 |
161| `fix` | Bug 修复 |
162| `docs` | 仅文档 |
163| `refactor` | 既不修复 bug 也不添加功能的代码改动 |
164| `test` | 添加或修复测试 |
165| `chore` | 构建流程、配置、CI、版本号提升 |
166| `style` | 格式化、空白（不改变逻辑） |
167
168示例：
169```
170feat: add EAN barcode scanning to Packaging module
171fix: prevent packed_qty from exceeding planned quantity
172docs: add supervisor guide
173chore: bump version to v0.3.7
174```

178<a id="issue-reporting"></a>
179## 问题反馈
180
181提交 issue 时，请包含：
182
183- **Version** —— 你运行的 OpenMES 版本
184- **Environment** —— Docker、裸机、操作系统、PHP 版本
185- **复现步骤** —— 触发问题的确切步骤
186- **预期行为** —— 应该发生什么
187- **实际行为** —— 实际发生了什么
188- **截图或日志** —— 如果有用的话
189
190对于安全漏洞，请**不要**开公开 issue。直接通过 **support@openmmes.com** 联系维护者。
