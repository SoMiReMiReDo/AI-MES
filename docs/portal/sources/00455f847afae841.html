1# feat(template-steps): add operation_type + flexible estimated_rate (value + unit) with conversions
2
3## Summary
4
5Add optional operation_type and a flexible estimated rate to process template steps:
6- `operation_type`: "batch" | "continuous"
7- `estimated_rate_value`: decimal (nullable)
8- `estimated_rate_unit`: enum string (nullable), supported values: pcs/min, pcs/hr, units/min, units/hr, batches/hr, kg/hr, litre/hr, litre/min
9- `normalized_rate_per_hour` & `normalized_rate_base_unit` (nullable) — populated when simple normalization is possible
10
11These fields are informational in this change; scheduling/estimators remain unchanged.
12
13## Why
14
15Recipes today only capture `estimated_duration_minutes`. Some processes are better expressed as rates (pcs/min, litre/hr, batches/hr). Supporting both batch vs continuous operation modes and flexible units makes templates more expressive and enables future scheduling and reporting improvements.
16

50## Cross-field Validation Rules
51
52Valid combinations of `operation_type` and `estimated_rate_unit`:
53
54| operation_type | allowed units | not allowed | notes |
55|---|---|---|---|
56| `"batch"` | batches/hr | pcs/*, units/*, kg/hr, litre/* | Batch operations use batch counts |
57| `"continuous"` | pcs/min, pcs/hr, units/min, units/hr, kg/hr, litre/min, litre/hr | batches/hr | Continuous operations use physical units only |
58| null (unspecified) | any | none | No validation applied if operation_type not set |
59
60**Enforcement:** These rules must be enforced consistently in API request validators, UI validators, and normalization service. Invalid combinations are rejected at create/update time.

62## Rate Field Constraints
63
64### `estimated_rate_value` & `estimated_rate_unit` (Presence-Aware)
65
66**Both fields are optional, but must follow presence-aware rules:**
67
681. **Both omitted or null**: Valid (rate not specified)
692. **One field present (non-null), one missing/null**: Invalid—reject with validation error
703. **Both present with non-null values (including zero)**: Valid; apply all constraints below
71
72**When both fields are present:**
73
74### `estimated_rate_value` (decimal(10,4))
75- **Range**: Non-negative (≥ 0), including zero (0.0000)
76- **Minimum non-zero**: 0.0001 (scale 4)
77- **Maximum**: 999999.9999
78- **Validation regex**: `/^\d+(\.\d{1,4})?$/` (enforces up to 4 decimal places)
79- **Validation rule**: `numeric|min:0|max:999999.9999|regex:/^\d+(\.\d{1,4})?$/`
80
81### `estimated_rate_unit` (enum string)
82- **Allowed values**: pcs/min, pcs/hr, units/min, units/hr, batches/hr, kg/hr, litre/hr, litre/min
83- **Validation rule**: `in:pcs/min,pcs/hr,units/min,units/hr,batches/hr,kg/hr,litre/hr,litre/min`
84- **Cross-field**: Must comply with operation_type rules (see above)
85
86### `normalized_rate_per_hour` (decimal(14,6), computed)
87- **Range**: Non-negative (≥ 0)
88- **Precision**: 14 digits, scale 6 (e.g., 9999999.999999)
89- **Rounding**: HALF_UP for all conversions
90- **Null handling**: Nullable; populated only when normalization succeeds
91- **Server-computed**: Do not accept client submissions unless explicitly supported
92
93### `normalized_rate_base_unit` (string, computed)
94- **Values**: null | "pcs/hr" | "litre/hr" | "kg/hr" | "batches/hr"
95- **Null handling**: Set to null if normalization not possible or source is cleared
96- **Server-computed**: Derived from estimated_rate_unit normalization rules
97
98## Supported units and normalization
99
100### Count units
101- pcs/min, pcs/hr, units/min, units/hr → **normalized to per-hour**
102 - Formula: value * 60 (for /min) or value (for /hr)
103 - `normalized_rate_base_unit` = "pcs/hr"
104 - Always succeeds, result cannot be null
105
106### Volume/mass units
107- litre/min → litre/hr
108 - Formula: value * 60
109 - `normalized_rate_base_unit` = "litre/hr"
110- kg/hr → unchanged
111 - Formula: value (no conversion needed)
112 - `normalized_rate_base_unit` = "kg/hr"
113
114### Batch units
115- batches/hr → pcs/hr (only with batch_size context)
116 - **Requires**: Product-level metadata (`batch_size`) available
117 - **batch_size type & constraints:**
118 - Type: positive decimal (unsigned)
119 - Precision: 10 digits, scale 4 (e.g., 9999.9999)
120 - Minimum: > 0
121 - Maximum: 9999.9999
122 - **Overflow behavior:** If `estimated_rate_value * batch_size > 999999.999999` (normalized_rate_per_hour max), API rejects the input with validation error before persisting; normalized fields remain null
123 - Formula: value * batch_size
124 - `normalized_rate_base_unit` = "pcs/hr"
125 - **When unavailable**: Both normalized fields remain `null`
126 - **Test coverage:** Add boundary tests for largest valid batch rate (e.g., 99999.9999 batches/hr * 9999.9999 batch_size)
127 - Do not attempt without product context
128
129### Conversions requiring product context
130- Conversions between batches ↔ pcs, kg ↔ pcs are **not attempted** without product-level metadata
131- If context becomes unavailable during update, clear normalized fields
132

137## Normalization Invariant & Field Invalidation
138
139### Create / Update Flow
1401. **Input validation**: Validate estimated_rate_value, estimated_rate_unit, presence-aware rules, cross-field rules
1412. **Normalization**: Compute normalized_rate_per_hour and normalized_rate_base_unit if conversion succeeds
1423. **Overflow check**: Reject if normalized result exceeds max decimal(14,6)
1434. **Persist**: Store all fields (nullable normalized fields if conversion not possible)
144
145### Invalidation Rules
146- **When estimated_rate_value or estimated_rate_unit changes**: Recompute normalized fields
147- **When estimated_rate_value is cleared (set to null)**: Clear both normalized fields; if estimated_rate_unit is not also cleared, reject with validation error (presence-aware)
148- **When conversion context becomes unavailable** (e.g., product batch_size removed): Clear normalized fields and log reason
149- **When operation_type changes**: Revalidate cross-field rules; reject if new type incompatible with current unit
150
151### API Consistency
152- API responses must never expose stale normalized values
153- Add tests covering: create, update, clear, context-change scenarios
154- **Regression tests for presence-aware validation:**
155 - Both fields omitted → accepted
156 - Both fields null → accepted
157 - estimated_rate_value present, estimated_rate_unit null → rejected
158 - estimated_rate_unit present, estimated_rate_value null → rejected
159 - Both present with zero value → accepted and normalized correctly
160 - Both present with max batch rate → overflow check tested
